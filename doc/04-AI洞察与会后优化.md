# AI 洞察与会后优化

> 主要实现：[`Sources/Insights/InsightEngine.swift`](../Sources/Insights/InsightEngine.swift)、[`Sources/Insights/InsightModels.swift`](../Sources/Insights/InsightModels.swift)、[`Sources/Insights/LLMProvider.swift`](../Sources/Insights/LLMProvider.swift)、[`Sources/Insights/OpenAICompatibleProvider.swift`](../Sources/Insights/OpenAICompatibleProvider.swift)、[`Sources/Insights/InsightSettings.swift`](../Sources/Insights/InsightSettings.swift)。

## 1. 能力边界

AI 能力是可选增强层，不参与实时字幕正确性：

- 未配置 API Key 时，音频采集、ASR、本地翻译、保存和导出仍然工作。
- 配置后，transcript 文字会发送给用户选择的服务商。
- 音频不会由这条链路上传。

设置本身就是启用开关，没有额外布尔开关。

## 2. 最小 provider 抽象

[`InsightProvider`](../Sources/Insights/LLMProvider.swift) 只有一个方法：

```swift
func complete(system: String, user: String) async throws -> String
```

所有内置服务商都使用 OpenAI 兼容的 `/chat/completions`，所以项目只有一个 `OpenAICompatibleProvider`。服务商差异集中在 `LLMProviderConfig`：base URL、默认模型、温度上限和 JSON 约束。

当前内置：DeepSeek、通义千问、智谱 GLM、Kimi，以及用户自定义的 OpenAI 兼容 endpoint。

HTTP 请求特点：

- 非流式。
- 30 秒超时。
- `temperature=0.3`，必要时按服务商上限裁剪。
- 强制 `response_format: {type: "json_object"}`。
- 将 401/403、429、其他 HTTP、网络、解析和空内容映射成用户可读 `LLMError`。

## 3. 洞察结构是一份模型、三处复用

[`InsightResult`](../Sources/Insights/InsightModels.swift) 同时是：

1. prompt 要求的 JSON schema。
2. SwiftUI 卡片的数据源。
3. `MeetingRecord.insightJSON` 的持久化载荷。

字段包括：当前话题、建议、参考回答、待办和决定。解码允许模型遗漏空字段，避免一个可选字段缺失导致整次结果作废。

UI 直接渲染类型化卡片，不引入 Markdown/HTML renderer。

## 4. 实时洞察触发

只消费 final ASR 内容，不消费 interim：

- speaker 发生切换时触发。
- 或累计 6 个新 final 句子时触发。

传给模型的是完整的当前 `sourceText` transcript，格式为 `我：...` / `对方：...`。它不用实时译文做事实来源，减少翻译误差的二次放大。

### 4.1 单飞 + dirty 合并

`InsightEngine` 同一时间只允许一个请求：

- 请求执行中若有新内容，只置 `dirtyDuringGen=true`。
- 当前请求结束后，最多立即再跑一次最新完整快照。
- 不为每次变化排一个请求。

这个设计与翻译邮箱共享同一种思想：实时系统关心“最新状态”，不关心重放所有中间快照。

## 5. 历史洞察

选择历史会议后：

- 已缓存洞察立即显示。
- 用户可以手动生成或重新生成。
- 结果写回 `insightJSON`，下次打开无需再请求。
- Markdown 导出会把洞察放在完整 transcript 前面。

实时洞察目前不会在会话结束时自动写入 `MeetingRecord.insightJSON`；历史缓存来自历史页的显式生成。

## 6. 会后优化

会后优化的目标不同于洞察：它逐行清理 ASR 原文，并在英文会议中重新翻译。

### 6.1 批处理策略

- 每批最多 8 行、约 1500 字符。
- 串行处理各批，控制输出规模和服务稳定性。
- 下一批携带上一批最后 2 行作为只读上下文。
- 累积术语表跨批传递，保持专有名词一致。

### 6.2 语言差异

- 英文会议：保守清理 source，结合上下文重做中文 target。
- 中文会议：更积极地补标点、去重复、恢复中英混杂术语，只返回 source；调用方把它镜像到 refined target。

两种 prompt 都明确要求不虚构事实。

### 6.3 部分成功

每批独立容错：

- 某批失败时跳过，该批行继续使用原始文本。
- 其他成功批仍然保留。
- 只有全部批次都失败时，整次操作才报错。

结果用 `orderIndex` 回写到 `refinedSource/refinedTarget`。这种 additive 设计使用户永远能回到原始记录，也让不完整优化安全降级。

## 7. 配置与密钥

- provider id、自定义 URL、自定义模型保存在 UserDefaults。
- API Key 作为 generic password 保存在 Keychain。
- 设置界面使用草稿态；只有点击保存才修改共享设置。
- 可用草稿配置先做一次连接测试。
- ATS 只显式允许 local networking；外部服务仍要求 HTTPS。

## 8. 需要认识的风险

- prompt 输入是截至当前的完整 transcript，实时洞察没有上下文 token 预算或截断策略；长会议可能超过模型窗口。
- `/chat/completions` 的“兼容”程度由服务商决定；当前固定要求 `json_object`，并非所有自定义 endpoint 都一定支持。
- `parse` 会容忍代码围栏或前后多余文本，但只提取最外层 `{...}`，复杂异常输出仍可能失败。
- 实时洞察在 speaker 切换时可能比较频繁，虽然单飞合并能防堆积，但没有时间冷却或费用预算。
- 用户必须清楚云端边界；“全程离线”只能描述未启用 AI 的实时字幕功能。
