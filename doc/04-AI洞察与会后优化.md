# AI 洞察与会后优化

> 主要实现：[`Sources/Insights/InsightEngine.swift`](../Sources/Insights/InsightEngine.swift)、[`Sources/Insights/TranscriptRefiner.swift`](../Sources/Insights/TranscriptRefiner.swift)、[`Sources/Insights/MeetingTitleGenerator.swift`](../Sources/Insights/MeetingTitleGenerator.swift)、[`Sources/Insights/VocabularyGenerator.swift`](../Sources/Insights/VocabularyGenerator.swift)、[`Sources/Capture/VocabularyImportController.swift`](../Sources/Capture/VocabularyImportController.swift)、[`Sources/Capture/VocabularyImportWindow.swift`](../Sources/Capture/VocabularyImportWindow.swift)、[`Sources/Insights/InsightModels.swift`](../Sources/Insights/InsightModels.swift)、[`Sources/AI/LLMProvider.swift`](../Sources/AI/LLMProvider.swift)、[`Sources/AI/OpenAICompatibleProvider.swift`](../Sources/AI/OpenAICompatibleProvider.swift)、[`Sources/AI/AISettings.swift`](../Sources/AI/AISettings.swift)。

## 1. 能力边界

AI 能力是可选增强层，不参与实时字幕正确性：

- 未配置 API Key 时，音频采集、ASR、本地翻译、保存和导出仍然工作。
- 配置后，transcript 文字会发送给用户选择的服务商。
- 用户在词表页明确选择 Markdown 文件生成候选词时，所选文件正文会分批发送给用户选择的服务商；文件名不发送，正文、来源摘录和未保存候选只保留在本次窗口的内存中；用户明确保存的词条写入本机词表。
- 用户发起会后优化时，当前完整的已保存词表会随优化 prompt 发送；智能洞察只发送当前最近上下文中命中的词条；标题请求不发送词表。
- 音频不会由这条链路上传。

设置中的“AI 服务”是全应用共享配置，统一供智能洞察、会后优化、会议标题和 Markdown 词表生成使用。智能洞察是其中一个依赖 AI 的功能；它不拥有或代理其他功能的配置状态。配置完整并保存后，各功能按原有触发方式使用服务，没有额外启用开关。

共享配置、provider、严格响应解析和 AI 设置页位于 `Sources/AI/`；设置窗口及跨页面导航由 `Sources/App/SettingsView.swift` 负责。`AppDelegate` 只创建一份 `AISettings` 并注入所有消费者，界面的可用性直接读取它，不再通过 `InsightEngine` 判断其他 AI 功能是否可用。

## 2. 最小 provider 抽象

[`LLMProvider`](../Sources/AI/LLMProvider.swift) 只有一个方法：

```swift
func complete(system: String, user: String, schema: LLMResponseSchema) async throws -> String
```

所有内置服务商都使用 OpenAI 兼容的 `/chat/completions` Structured Outputs，所以项目只有一个 `OpenAICompatibleProvider`。调用方拥有业务 Schema，provider 只负责把它编码到请求。

当前内置只保留已明确支持严格 Schema 的通义千问 `qwen3.8-flash` 和 Kimi `kimi-k3`，另支持用户自定义的 OpenAI-compatible endpoint。DeepSeek 和智谱 GLM 的旧 JSON Object 路径已删除。

HTTP 请求特点：

- 非流式。
- AI 生成请求统一设置 60 秒请求超时，适用于词表、洞察、会后优化、标题和连接测试；词表每次重试沿用该设置，串行处理和最多 2 次重试不变。模型列表查询仍使用 30 秒超时。
- `temperature=0.3`，必要时按服务商上限裁剪。
- 每次请求强制 `response_format: {type: "json_schema", json_schema: {strict: true, ...}}`。
- 检查 `finish_reason`，把截断、内容拒绝、400 Schema/参数错误与其他 HTTP、网络、解析、空内容分别映射成用户可读 `LLMError`。

## 3. 洞察结构是一份模型、三处复用

[`InsightResult`](../Sources/Insights/InsightModels.swift) 同时是：

1. 发送给模型的严格 JSON Schema。
2. SwiftUI 卡片的数据源。
3. `MeetingRecord.insightJSON` 的持久化载荷。

字段包括：当前话题、建议、参考回答、待办和决定。所有键都必须出现，没有参考回答时 `answer` 为 `null`，其他空值用空字符串或空数组表达；字段缺失、类型错误或建议超过 3 条时客户端拒绝整个结果。

UI 直接渲染类型化卡片，不引入 Markdown/HTML renderer。

## 4. 实时洞察触发

只消费 final ASR 内容，不消费 interim：

- speaker 发生切换时触发。
- 或累计 6 个新 final 句子时触发。

传给模型的是当前 `sourceText` transcript 中最新的完整行，格式为 `我：...` / `对方：...`。输入最多 6000 个 Swift 字符，为内置最小 8K 上下文模型保留 system prompt 和输出空间；如果单行已超过上限，保留该行的最新后缀。洞察不用实时译文做事实来源，减少翻译误差的二次放大。

每个实时或历史洞察请求开始时，`InsightEngine` 在这份已截断的最近上下文中匹配当前已保存词表。匹配忽略大小写，字母或数字开头/结尾的词条还必须满足字母数字边界，因此 `PR` 不会在 `project` 中误命中。只有命中词条按用户保存的顺序和精确拼写进入 system prompt；模型只能在需要提及时保持该拼写，不得强行植入对话中没有的信息。词表为空或无命中时不增加这段 prompt。

### 4.1 单飞 + dirty 合并

`InsightEngine` 同一时间只允许一个请求：

- 请求执行中若有新内容，只置 `dirtyDuringGen=true`。
- 当前请求结束后，最多立即再跑一次最新完整快照。
- 不为每次变化排一个请求。

这个设计与翻译邮箱共享同一种思想：实时系统关心“最新状态”，不关心重放所有中间快照。

每个实时生成还绑定 `liveToken`。开始新会议或重置引擎时会取消任务并更换 token，即使旧 provider 迟到返回，也不能更新新会议的洞察卡片。

## 5. 历史洞察

选择历史会议后：

- 已缓存洞察立即显示。
- 用户可以手动生成或重新生成。
- 生成时每行优先使用非空的 `refinedSource`，没有成功优化的行回退到 `sourceText`；不使用译文作为事实来源。实时洞察和会议标题仍使用原始 `sourceText`。
- 结果写回 `insightJSON`，下次打开无需再请求。
- Markdown 导出会把洞察放在完整 transcript 前面。
- 切换或删除当前历史会议时取消生成任务；回写前再校验选中记录和操作 token，避免旧请求污染新页面。

实时洞察目前不会在会话结束时自动写入 `MeetingRecord.insightJSON`；历史缓存来自历史页的显式生成。

## 6. 会后优化

会后优化的目标不同于洞察：它逐行清理 ASR 原文，并在源语言与目标语言不同时按原方向重新翻译。这个用例由独立的 [`TranscriptRefiner`](../Sources/Insights/TranscriptRefiner.swift) 拥有；`InsightEngine` 只处理结构化洞察，两者复用同一 provider 设置但不共享状态机。

用户开始优化时，[`MeetingTitleGenerator`](../Sources/Insights/MeetingTitleGenerator.swift) 同时发起另一条独立 HTTP 请求。标题生成不进入逐批优化状态机，也不等待优化稿完成。

### 6.1 批处理策略

- 每批最多 8 行、约 1500 字符。
- 串行处理各批，控制输出规模和服务稳定性。
- 下一批携带上一批最后 2 行作为只读上下文。
- 操作开始时冻结当前已保存的用户词表，并把同一份专有词提示传给每个批次；运行中修改设置不会让前后批次使用不同版本。
- 累积术语表跨批传递，保持专有名词一致。

### 6.2 语言差异

- 不同语言：prompt 明确源语言和目标语言，保守清理 source，并结合上下文按所选方向重做 target。
- 相同语言：prompt 明确禁止翻译，只清理 source；调用方把结果镜像到 refined target。
- 用户词表只在对话内容匹配时用于纠正 source 的专有词拼写，不会强行植入未出现的词；已有 AI 术语表中的 target 映射优先，未约定译名的品牌、产品、人名和缩写保留原文。
- 输入中的说话人标签只用于提供上下文；模型若把“我/对方/Me/Other party”连同冒号回显到 source 或 target，解析边界会在持久化前移除该行首标签，正文中的正常第一人称表达不受影响。

两种 prompt 都明确要求不虚构事实。

### 6.3 部分成功

每批独立容错：

- 某批失败时跳过，该批行继续使用原始文本。
- 其他成功批仍然保留。
- 只有全部批次都失败时，整次操作才报错。

结果用 `orderIndex` 回写到 `refinedSource/refinedTarget`。这种 additive 设计使用户永远能回到原始记录，也让不完整优化安全降级。

切换记录时，界面任务和 `TranscriptRefiner` 的 run token 同时失效。provider 恢复后必须通过任务取消、run token 和当前选中 record id 三重校验，才能修改 SwiftData。

### 6.4 会议标题

- 标题请求使用按时间排序的 ASR 源文，最多发送最新 6000 个字符，因此可以与译文优化并行。
- 标题请求使用独立 `meeting_title` Schema；prompt 同时简述字段语义和内容限制，客户端拒绝空标题并把异常长输出截到 30 个字符。
- 标题和优化结果独立处理、独立保存。标题失败不会让优化失败；优化失败也不会丢弃已成功的标题。
- 只有记录尚无有效 `aiTitle` 时才生成标题；成功持久化后，“重新优化”只处理译文，不再产生标题请求。此前标题请求失败时，下一次重新优化会继续尝试。
- 切换记录会取消两条任务，回写前都校验操作 token 和当前记录 id，防止迟到结果污染其他会议。
- `MeetingRecord.aiTitle` 持久化成功标题。历史侧栏和详情页优先显示它，同时保留开始时间作为次要信息；没有有效标题时仍回退到开始时间。

### 6.5 统一 JSON 边界

洞察、优化、标题和连接测试共用严格 `JSONResponseParser`：只对完整的 assistant content 执行 `JSONDecoder`，不再提取 markdown code fence、外围文字或容忍缺失字段。每次仍发送 strict Schema；prompt 用一句话同步字段语义，使会接受但不会真正执行 `response_format` 的兼容网关也有机会生成正确结构。这不是 JSON Object 降级，非法结果仍整体失败并显示独立的 Schema 契约错误。

## 7. 配置与密钥

- provider id、自定义 API 地址、自定义模型保存在 UserDefaults。
- API Key 作为 generic password 保存在 Keychain，service 使用应用 bundle ID `com.plus.samewave`。旧身份下的设置和密钥不会自动读取或迁移，安装改名版后需重新配置。
- 设置界面使用草稿态；只有点击保存才修改共享设置。
- 设置窗口的“AI 服务”页明确展示配置的全应用用途；洞察面板、历史优化和词表页的“配置 AI 服务”入口都定位到该 Tab，即使此前停留在词表页。跳转不提交词表的手动草稿。自定义配置内容可滚动，保存/取消固定在底部。
- `AISettings` 统一校验保存配置与测试连接草稿：所有服务均需非空密钥，自定义服务还需有效地址和非空模型 ID。配置存储仍使用同一组 UserDefaults 键与 Keychain 账户，没有新增配置副本或迁移分支。
- 可用草稿配置先做一次带嵌套对象和数组的 Schema 连接测试，确认 endpoint/模型能端到端返回应用实际需要的结构，而不是用一个碰巧符合的简单对象产生假阳性。
- 自定义 API 地址允许填写裸域名或主机、带版本路径的 base URL，以及完整的 `/chat/completions` 地址。裸远程主机默认使用 HTTPS 和 `/v1/chat/completions`；localhost 与回环地址默认使用 HTTP；界面始终显示规范化后的实际请求 URL。
- 模型列表从实际 Chat Completions 地址的同级 `/models` 获取，并使用相同的 Bearer API Key。成功后用户可从菜单选择模型，同时保留模型 ID 手动输入；服务返回 404/405、空列表或非标准响应时不会阻塞配置。
- ATS 只显式允许 local networking；外部服务仍要求 HTTPS。
- 设置窗口另有独立的“词表”Tab；词表用于本地英文识别，会后优化使用操作开始时完整的已保存词表，实时与历史智能洞察仅使用当前上下文命中的词条，标题请求不使用词表。空词表或空命中不会增加洞察提示内容。
- 词表 Tab 只提供“从 Markdown 生成”入口。点击后直接显示系统文件选择器，选中文件后才打开独立小窗；生成进度、失败披露和新词审核都在该窗口内完成。取消首次选择不会启动任务；选中后切换 Tab 或关闭设置窗口不会影响任务。关闭生成窗口会取消请求并丢弃尚未确认的审核内容；点击“停止”会取消当前及待发请求，保留窗口和已生成候选，无候选时回到文件选择界面。窗口使用实际 NSWindow 关闭通知取消工作，状态切换、隐藏窗口和 Settings 生命周期不触发取消。
- AI 配置完成后，可多选 UTF-8 `.md` / `.markdown` 文件生成候选词，单个文件最多 3 MB，一次选择总计最多 30 MB。应用不设置正文字符总量限制；本地先用最多 18000 字符的内部片段处理超长段落，再组装成每个最多 20000 字符的实际 AI 请求。请求严格串行，每个首次失败后再重试 2 次；重试耗尽则记录并跳过该请求，继续处理后续内容。每个成功请求通过独立 strict Schema 返回最多 50 个单行词条。Markdown 被视为不受信任数据，system prompt 明确禁止执行文档内指令。提取采用“具体命名实体”和“语音识别价值”双门槛，普通技术概念、功能类别、流程词及仅因标题化或全大写而显眼的短语必须排除，不确定时返回更少或空结果。
- 每个请求成功即发布候选，排除已保存词表、当前设置草稿和本次已见词条中的重复项。审核列表默认勾选，支持编辑、全选/全不选及展开本地来源文件名和原文摘录；没有匹配到原文时明确提示核对，不编造来源。词条保持稳定 ID 和原始提取身份，后续请求不覆盖用户编辑和勾选状态。
- “添加并保存 N 个词”在本窗口直接持久化选中的新词，保存时重新去重；只将新增词追加到设置草稿，保留其他手动增删和文本格式，不顺带提交它们。生成期间也可保存，保存反馈内联展示。
- 每个请求保留成功、失败或待处理状态。“重试未完成部分”仅重发失败、中断和未发出的请求，各自重新获得首次尝试加 2 次重试，成功请求不重复付费；保留审核编辑、来源和历史尝试记录。服务商配置在最初操作开始时冻结，重试不切换配置。停止使运行 token 失效，迟到响应不能进入审核，重新运行会等待旧任务取消完成以维持串行。
- 默认只显示完成数、新词数和当前重试状态。“请求详情”逐次记录成功、错误、停止及耗时：使用单调时钟，计时从 provider 调用前到完整响应及词条校验结束，不包含重试间隔；这是网络与服务端合计时间，不能据此细分模型推理、服务排队或网络延迟。读取和分片在后台进行，取消会传递到后台任务。

## 8. 需要认识的风险

- 应用不会在请求中设置或发现模型的上下文窗口；窗口由所选模型和服务端决定。洞察和标题使用 6000 字符预算，Markdown 词表每个请求的正文使用 20000 字符预算；字符数不是精确 token 计数，完整请求还包括 system prompt、Schema 和输出。
- `/chat/completions` 的“兼容”不代表网关会真正强制 `json_schema`。自定义 endpoint/模型应先通过代表性连接测试；所有正式请求仍发送 Schema 并严格解码，不会降级到 JSON Object，但忽略 Schema 的网关仍可能偶发失败。
- `/models` 是辅助能力，不是所有兼容服务都会实现，也有网关使用不同的模型发现路径；这类服务必须手动填写模型 ID。
- 严格 Schema 仍不保证内容事实正确；客户端继续校验空标题、批次行号和洞察建议数量等业务不变量。
- 实时洞察在 speaker 切换时可能比较频繁，虽然单飞合并能防堆积，但没有时间冷却或费用预算。
- 较长 Markdown 会拆成多次 AI 请求，产生相应延迟和费用。单个请求重试 2 次后仍失败会被跳过，因此审核结果可能只来自部分文档内容；审核窗口会明确披露这种情况。
- 命中的词表内容可能包含内部项目名或人名，会作为智能洞察 system prompt 的一部分发送给所选服务商。
- 用户必须清楚云端边界；“全程离线”只能描述未启用 AI 的实时字幕功能。
