# AI 洞察与会后优化

> 主要实现：[`Sources/Insights/InsightEngine.swift`](../Sources/Insights/InsightEngine.swift)、[`Sources/Insights/TranscriptRefiner.swift`](../Sources/Insights/TranscriptRefiner.swift)、[`Sources/Insights/InsightModels.swift`](../Sources/Insights/InsightModels.swift)、[`Sources/Insights/LLMProvider.swift`](../Sources/Insights/LLMProvider.swift)、[`Sources/Insights/OpenAICompatibleProvider.swift`](../Sources/Insights/OpenAICompatibleProvider.swift)、[`Sources/Insights/InsightSettings.swift`](../Sources/Insights/InsightSettings.swift)。

## 1. 能力边界

AI 能力是可选增强层，不参与实时字幕正确性：

- 未配置 API Key 时，音频采集、ASR、本地翻译、保存和导出仍然工作。
- 配置后，transcript 文字会发送给用户选择的服务商。
- 音频不会由这条链路上传。

设置本身就是启用开关，没有额外布尔开关。

## 2. 最小 provider 抽象

[`InsightProvider`](../Sources/Insights/LLMProvider.swift) 只有一个方法：

```swift
func complete(system: String, user: String) async throws -> String
```

所有内置服务商都使用 OpenAI 兼容的 `/chat/completions`，所以项目只有一个 `OpenAICompatibleProvider`。服务商差异集中在 `LLMProviderConfig`：完整请求地址、默认模型、温度上限和 JSON 约束。

当前内置：DeepSeek、通义千问、智谱 GLM、Kimi，以及用户自定义的 OpenAI 兼容 endpoint。

HTTP 请求特点：

- 非流式。
- 30 秒超时。
- `temperature=0.3`，必要时按服务商上限裁剪。
- 强制 `response_format: {type: "json_object"}`。
- 将 401/403、429、其他 HTTP、网络、解析和空内容映射成用户可读 `LLMError`。

## 3. 洞察结构是一份模型、三处复用

[`InsightResult`](../Sources/Insights/InsightModels.swift) 同时是：

1. prompt 要求的 JSON schema。
2. SwiftUI 卡片的数据源。
3. `MeetingRecord.insightJSON` 的持久化载荷。

字段包括：当前话题、建议、参考回答、待办和决定。解码允许模型遗漏空字段，避免一个可选字段缺失导致整次结果作废。

UI 直接渲染类型化卡片，不引入 Markdown/HTML renderer。

## 4. 实时洞察触发

只消费 final ASR 内容，不消费 interim：

- speaker 发生切换时触发。
- 或累计 6 个新 final 句子时触发。

传给模型的是当前 `sourceText` transcript 中最新的完整行，格式为 `我：...` / `对方：...`。输入最多 6000 个 Swift 字符，为内置最小 8K 上下文模型保留 system prompt 和输出空间；如果单行已超过上限，保留该行的最新后缀。洞察不用实时译文做事实来源，减少翻译误差的二次放大。

### 4.1 单飞 + dirty 合并

`InsightEngine` 同一时间只允许一个请求：

- 请求执行中若有新内容，只置 `dirtyDuringGen=true`。
- 当前请求结束后，最多立即再跑一次最新完整快照。
- 不为每次变化排一个请求。

这个设计与翻译邮箱共享同一种思想：实时系统关心“最新状态”，不关心重放所有中间快照。

每个实时生成还绑定 `liveToken`。开始新会议或重置引擎时会取消任务并更换 token，即使旧 provider 迟到返回，也不能更新新会议的洞察卡片。

## 5. 历史洞察

选择历史会议后：

- 已缓存洞察立即显示。
- 用户可以手动生成或重新生成。
- 结果写回 `insightJSON`，下次打开无需再请求。
- Markdown 导出会把洞察放在完整 transcript 前面。
- 切换或删除当前历史会议时取消生成任务；回写前再校验选中记录和操作 token，避免旧请求污染新页面。

实时洞察目前不会在会话结束时自动写入 `MeetingRecord.insightJSON`；历史缓存来自历史页的显式生成。

## 6. 会后优化

会后优化的目标不同于洞察：它逐行清理 ASR 原文，并在源语言与目标语言不同时按原方向重新翻译。这个用例由独立的 [`TranscriptRefiner`](../Sources/Insights/TranscriptRefiner.swift) 拥有；`InsightEngine` 只处理结构化洞察，两者复用同一 provider 设置但不共享状态机。

### 6.1 批处理策略

- 每批最多 8 行、约 1500 字符。
- 串行处理各批，控制输出规模和服务稳定性。
- 下一批携带上一批最后 2 行作为只读上下文。
- 累积术语表跨批传递，保持专有名词一致。

### 6.2 语言差异

- 不同语言：prompt 明确源语言和目标语言，保守清理 source，并结合上下文按所选方向重做 target。
- 相同语言：prompt 明确禁止翻译，只清理 source；调用方把结果镜像到 refined target。

两种 prompt 都明确要求不虚构事实。

### 6.3 部分成功

每批独立容错：

- 某批失败时跳过，该批行继续使用原始文本。
- 其他成功批仍然保留。
- 只有全部批次都失败时，整次操作才报错。

结果用 `orderIndex` 回写到 `refinedSource/refinedTarget`。这种 additive 设计使用户永远能回到原始记录，也让不完整优化安全降级。

切换记录时，界面任务和 `TranscriptRefiner` 的 run token 同时失效。provider 恢复后必须通过任务取消、run token 和当前选中 record id 三重校验，才能修改 SwiftData。

### 6.4 统一 JSON 边界

洞察和优化共用 `JSONResponseParser`：先直接解码，再容忍 markdown code fence 或外围文字并提取最外层 JSON object。这是 provider 输出边界的宽容处理，不会把解码失败当成成功。

## 7. 配置与密钥

- provider id、自定义 API 地址、自定义模型保存在 UserDefaults。
- API Key 作为 generic password 保存在 Keychain。
- 设置界面使用草稿态；只有点击保存才修改共享设置。
- 可用草稿配置先做一次连接测试。
- 自定义 API 地址允许填写裸域名或主机、带版本路径的 base URL，以及完整的 `/chat/completions` 地址。裸远程主机默认使用 HTTPS 和 `/v1/chat/completions`；localhost 与回环地址默认使用 HTTP；界面始终显示规范化后的实际请求 URL。
- 模型列表从实际 Chat Completions 地址的同级 `/models` 获取，并使用相同的 Bearer API Key。成功后用户可从菜单选择模型，同时保留模型 ID 手动输入；服务返回 404/405、空列表或非标准响应时不会阻塞配置。
- ATS 只显式允许 local networking；外部服务仍要求 HTTPS。
- 设置窗口另有独立的“词表”Tab；它只配置本地英文语音识别，不会把词表发送给 AI 服务商。

## 8. 需要认识的风险

- 6000 字符是与 provider 无关的保守预算，不是每个模型的精确 tokenizer；长会议的洞察刻意优先最新话题，不保证覆盖很早的内容。
- `/chat/completions` 的“兼容”程度由服务商决定；当前固定要求 `json_object`，并非所有自定义 endpoint 都一定支持。
- `/models` 是辅助能力，不是所有兼容服务都会实现，也有网关使用不同的模型发现路径；这类服务必须手动填写模型 ID。
- `parse` 会容忍代码围栏或前后多余文本，但只提取最外层 `{...}`，复杂异常输出仍可能失败。
- 实时洞察在 speaker 切换时可能比较频繁，虽然单飞合并能防堆积，但没有时间冷却或费用预算。
- 用户必须清楚云端边界；“全程离线”只能描述未启用 AI 的实时字幕功能。
