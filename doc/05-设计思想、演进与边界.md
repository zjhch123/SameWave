# 设计思想、演进与边界

## 1. 从源码反推的核心思想

### 1.1 用系统边界减少算法问题

最有价值的选择不是某个模型，而是把“我”和“对方”放在两个输入通道。对于一对一会议，物理来源已经提供了足够可靠的身份信息，因此主链路不需要引入 diarization 的模型体积、延迟和标签漂移。

这是一种明确的产品换技术：先收窄场景，再换取更简单、更确定的实现。

### 1.2 实时系统追求最新快照，而不是处理所有中间态

两个地方使用了相同模式：

- 翻译：同一 Section 的待处理请求被最新 generation 覆盖。
- 洞察：请求执行期间的所有变化合并为一个 dirty 标志。

interim ASR 本来就是易变假设，逐个保序处理不仅没有价值，还会制造延迟。系统把资源用于尽快追上用户此刻看到的状态。

### 1.3 将正交状态拆开

Section 的内容生命周期和翻译生命周期分别建模。`sealed` 不等于 `done`，因此换人、暂停或停止不会阻断已经开始的译文。这直接对应产品需求中的“分段与翻译正交”。

### 1.4 原始事实不可破坏

会后 AI 优化只写 `refinedSource/refinedTarget`，原始 ASR 和实时译文不被覆盖。这个原则同时支持：

- 用户核验 AI 是否改意。
- 部分批次失败时逐行回退。
- 原始/优化视图切换。
- 后续使用更好模型重新生成。

### 1.5 从第一秒开始保存

记录不是在“结束”按钮后才生成。start 即建立 SwiftData record，并以稳定 Section id 增量 upsert。这让暂停、崩溃恢复和多未结束会议自然建立在同一数据模型上。

### 1.6 让平台能力承担通用复杂度

主 target 没有第三方依赖：Apple 框架提供采集、识别、翻译、数据层和 UI。工程体积和供应链简单，但代价是绑定 macOS 26，并受系统 API 生命周期、语言资源和权限模型约束。

### 1.7 生命周期必须等待真实完成

暂停和结束不再用延时猜测后台工作是否完成。采集、有界音频流、Speech finalization、主 actor store 回调、翻译 in-flight 和 SwiftData save 都有明确边界。只有 Translation 因系统服务不可控而使用显式 5 秒上限，超时后保存原文并拒绝迟到回写。

## 2. 架构演进

当前产品已经从单一字幕工具演进为集实时转写、翻译、历史和可选 AI 洞察于一体的会议工作台：

| 初始方案 | 当前方案 | 动机/结果 |
|---|---|---|
| 按应用 Core Audio Process Tap | 捕获全部系统音频的 ScreenCaptureKit | 避免打开麦克风后远端音质下降；删除应用选择器 |
| WhisperKit / 多引擎选择 | 双 Apple SpeechAnalyzer | 两路使用统一 ASR，删除第三方模型依赖 |
| 菜单栏 + 悬浮字幕 NSPanel | Dock + 菜单栏入口 + 三栏主窗口 | 历史、字幕、洞察进入一个工作台 |
| 仅实时字幕/导出 | SwiftData 增量历史与恢复 | 从工具变成可持续会议记录产品 |
| 简单翻译队列 | 按 Section 合并邮箱 + generation | 控制高频 interim 带来的积压和乱序 |
| 本地字幕工具 | 可选 strict JSON Schema 洞察和优化 | 扩展会中辅助、会后整理能力 |
| 布尔组合会话状态 + 900ms 延时保存 | 显式生命周期 + 可等待收尾 | 防止非法转移、最后一句丢失和迟到污染 |
| unsafe Sendable + 最小并发检查 | actor/MainActor 隔离 + complete 检查 | 让编译器验证采集与识别边界 |
| 无测试 target | XCTest 领域回归集 | 固定 Section、调度、持久化和 AI 纯逻辑 |
| 单个洞察全能对象 | `InsightEngine` + `TranscriptRefiner` + `MeetingTitleGenerator` | 分离实时单飞、会后分批和单次标题三种执行语义 |

这些旧实现不再作为仓库中的可选路径；当前架构以 [`Sources/`](../Sources/) 和 [`project.yml`](../project.yml) 为准。

## 3. 需求与实现的关键张力

[对话渲染需求与状态机](会议实时翻译-对话渲染需求与状态机.md) 描述了显式 `IDLE/SINGLE/OVERLAP`、speech-start/speech-end 事件和封板后 correction-only。当前 ASR API 输出的是 interim/final 文本，而不是可靠的双路 VAD 事件，因此实现选择了 single floor + final commit 抢话权。

这个实现优点是简单、抗 partial 抖动、天然适合单列 UI；缺点是：

- 换段晚于实际打断开始。
- 真正重叠发言只能按两个 final 返回的先后被串行化。
- 没有明确实现封板后 ASR 回改。
- 长停顿不会独立结束轮次，同一说话人停顿后继续可能仍在同一 Section。

后续如果必须严格满足需求状态机，不能只在 `CaptionStore` 加一个枚举；需要先在采集/识别层提供可信的每路 speech start/end 事件，并定义重叠时 ASR 文本归属与 correction 语义。

## 4. 当前边界与技术债

### 4.1 产品边界

- 面向一对一；多个远端参与者都显示为“发言人”。
- 系统音频捕获是全局的，其他应用声音也可能进入 transcript。
- 语言范围固定为英语和简体中文，支持双向翻译；同语言组合直接显示识别结果。
- 不保存音频，无法重新跑 ASR 或进行事后说话人校正。
- macOS 26+，不是旧系统兼容产品。

### 4.2 工程边界

- 已有单元测试 target，覆盖 `CaptionStore`、`TranslationBridge`、SwiftData upsert/空记录删除、AI 上下文和 JSON 解析；真实 Speech、Translation、权限和 UI 仍没有自动化集成测试。
- Swift 6 主 target 和测试 target 都使用 `SWIFT_STRICT_CONCURRENCY=complete`。`NativeSpeechEngine` 是 actor，采集器和协调器在 MainActor；不使用 `@unchecked Sendable` 或 `nonisolated(unsafe)`。
- 主窗口已拆为容器、侧栏、舞台和洞察 Inspector。`CaptureCoordinator` 仍是会话纵向编排点；只在出现新的独立 I/O 或状态责任时继续拆分，不为减少行数增加协议和间接层。
- `build.sh` 硬编码个人 Apple Development 证书名称，不适合其他开发者直接使用。
- Translation drain 有 5 秒最长等待；超时优先保证会话可结束和原文可落盘，因此慢翻译可能只保留部分结果。
- 实时 AI 用 6000 字符的 provider-无关预算，这不是精确 token 计数，也意味着长会议洞察优先最新话题。
- 应用终止回调只能同步保存已进入 store 的快照，不能异步排空尚在 Speech 中的音频。

### 4.3 仓库与文档边界

- 产品源码只位于 [`Sources/`](../Sources/)；文档不应把仓库外的目录当成构建输入或运行依赖。
- [`project.yml`](../project.yml) 是工程配置的事实来源；生成的 `SameWave.xcodeproj` 不手工维护。
- 根 [`README.md`](../README.md) 面向使用者，本目录的 `01`–`06` 描述当前实现，需求文档保留产品基线，[`DECISIONS.md`](DECISIONS.md) 保留重要决策的原因。

## 5. 后续演进的判断顺序

遵循当前项目已经表现出的“先小闭环、再加一层”思想，建议按以下顺序判断新需求：

1. 它是否仍属于一对一、双物理通道场景？若不是，先重审身份模型。
2. 它是否会改变 Section 不变量？先写状态转换样例和测试，再动 UI。
3. 它是否需要所有中间事件，还是只需要最新快照？实时链路默认优先合并。
4. 它是否修改事实数据？AI 衍生结果应保持 additive。
5. 它是否影响崩溃恢复？从 start 时落盘的完整生命周期验证，而不是只测试正常 stop。
6. 它是否扩大数据出机范围？必须在设置和产品文案中显式体现。
